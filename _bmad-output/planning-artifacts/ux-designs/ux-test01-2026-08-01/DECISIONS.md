# Решения и допущения — test01

- **Дата:** 2026-08-08
- **Статус:** принято для реализации
- **Источник истины:** новый пользовательский бриф дополняет PRD и имеет приоритет в вопросах UX/UI; `DESIGN.md` отвечает за внешний вид, `EXPERIENCE.md` — за поведение.

## Решения

### D-01. Продолжить существующий UX-workspace

Использовать `_bmad-output/planning-artifacts/ux-designs/ux-test01-2026-08-01`, а не создавать параллельный набор контрактов. Старые функциональные решения и journeys сохраняются, визуальный и producer-side слой обновляются.

### D-02. Сохранить продуктовый контракт

Редизайн не меняет бизнес-логику MVP: покупателю не нужен аккаунт; связь остаётся Telegram-only; нет оплаты, доставки, внутреннего чата или marketplace discovery. Сохраняются состояния товара `draft`, `published`, `hidden`, `deleted`, правила 404, preview без аналитических событий, source attribution и существующие FR-1–FR-22 / UJ-1–UJ-5.

### D-03. Разделить public и seller-плотность

Публичная витрина получает редакционную композицию, крупную типографику и продукт как главный визуальный объект. Кабинет продавца становится плотным рабочим инструментом: sidebar на desktop, нижняя навигация на mobile, строки и разделители вместо набора больших карточек.

### D-04. Заменить liquid-glass как основной язык

Основной язык — монохромный neo-Swiss editorial-tech: тёплый почти белый фон, графитовый текст, нейтральная шкала, тонкие правила, минимум теней и один кобальтовый акцент. `backdrop-blur`, стеклянные панели, радиусы 20–28 px и pill-кнопки не используются как глобальная идентичность. Pill остаётся только у компактных фильтров/статусов.

### D-05. Цветовой акцент

Брендовый акцент — кобальтовый `#2457E6`; он используется для focus, links, active navigation, progress и текущего шага, но не для заливки кнопок. Все primary/Telegram action-кнопки используют чёрный `#171716` с белым текстом; secondary, ghost и destructive сохраняют свои функциональные варианты. Ошибки и успех используют семантические цвета вместе с текстом, не цветом одним.

### D-06. Кириллическая типографика

Основной variable grotesk — Onest (Cyrillic + Latin, OFL), близкий по характеру к Instrument Sans, но пригодный для русского текста. JetBrains Mono применяется только для номеров шагов, ID, статусов и метрик. Подключение выполняется через `next/font` с self-hosting в сборке; системный fallback остаётся обязательным.

### D-07. Четыре шага создания товара

Мастер: `Основное` → `Продажа` → `Фото` → `Проверка`. Stepper сообщает положение, а не заменяет навигацию. `Назад` и `Продолжить` сохраняют введённое; текущий шаг проверяется перед переходом; ошибки находятся рядом с полями и в summary; финал показывает покупательский preview и ссылки «Изменить» к каждому разделу.

Черновик создаётся не позднее перехода к загрузке фото, потому что storage path и media records требуют `productId`. Это допустимое техническое автосохранение: товар остаётся `draft` и не виден покупателю.

### D-08. Жизненный цикл фото

После выбора допустимого файла сразу появляется object-URL thumbnail и локальная валидация. Каждая принятая позиция имеет `queued`, `uploading`, `processing`, `success` или `error`, понятный progress, retry и удаление без потери соседних файлов; локально отклонённые файлы в очередь не попадают. Обложка выбирается явно; технически это перемещение media item на позицию 0, что сохраняет текущий backend-инвариант. Drag-and-drop может быть ускорителем, но кнопки «Выше/ниже» остаются обязательным keyboard/touch способом.

### D-09. Настройки магазина — разделы, не onboarding-stepper

Для регулярного редактирования применяются секции `Профиль`, `Публичная ссылка`, `Связь`, `О витрине`. На desktop справа закреплён live preview; на mobile preview открывается отдельной командой/маршрутом. Save/Discard появляется только при dirty state. Создание первой витрины использует ту же структуру без отдельной второй системы.

### D-10. App-native feedback

- `Dialog` — native `<dialog>.showModal()` с inert background, focus trap, Escape и возвратом фокуса. Для необратимого действия начальный фокус — на «Отмена»; для информационного mobile preview — на заголовке, чтобы длинный контент открывался с начала.
- `Toast/status` — краткий успех или фоновое завершение без переноса фокуса.
- `Alert` — срочная ошибка, требующая внимания.
- Inline error — ошибка конкретного поля с `aria-invalid` и `aria-describedby`.
- Error summary — многоошибочная отправка; получает фокус и ведёт к полям.

Browser-native `alert`, `confirm`, `prompt` не применяются.

### D-11. Состояния не смешиваются

Первый запуск, пустой результат фильтра, loading, локальная ошибка и permission/unavailable — разные состояния с разными следующими действиями. Skeleton повторяет будущую структуру. Повторная попытка локальна и сохраняет введённые данные.

### D-12. Responsive и доступность

Контрольные ширины: 320, 360, 390, 412, 430 px и desktop 1280+. Горизонтального скролла нет. Интерактивные цели — минимум 44×44 px. Mobile navigation учитывает `env(safe-area-inset-bottom)` и не закрывает сфокусированные элементы. `aria-current`, route titles, skip-link, логичный tab order, visible focus, reduced motion и контраст WCAG 2.2 AA обязательны.

### D-13. Реализация без новой UI-библиотеки

Использовать существующие React/Next/Tailwind/CVA primitives. Новую UI-библиотеку не добавлять. Нативный `<dialog>`, React state, Server Actions и Supabase-клиент достаточны; сторонний upload dependency допустим только если без него невозможно честно выполнить per-file progress после проверки существующего API.

### D-14. Локальная валидация и данные

Браузерные проверки выполняются только против локального Supabase. Для E2E разрешены локальные `seller@example.com`, витрина `studio-01` и тестовые товары/фото. Production deployment, production data и внешние сообщения исключены.

### D-15. Идемпотентность и безопасная навигация мастера

Создание черновика получает детерминированный UUID на стабильный request ID, поэтому повтор одного намерения переиспользует тот же draft. Media Route Handler принимает один файл, требует конечный положительный `Content-Length` и стабильный `uploadId`; retry сначала ищет уже сохранённый результат и не создаёт дубликат. Upload выполняется строго последовательно (`concurrency = 1`). Пока media queue занята, кнопки шага и browser Back/Forward не уводят пользователя от доступных progress/error states; возврат к Review дополнительно валидирует текущий snapshot и открывает первый ошибочный шаг.

### D-16. Чёрный цвет кнопочных действий

Пользовательский override от 2026-08-08 заменяет синюю заливку всех кнопочных primary actions на чёрную. Общий `Button` (включая `telegram`), псевдокнопка file input и active marker кнопочного catalog toggle используют отдельный action-token, чтобы не перекрашивать кобальтовые focus rings, ссылки, navigation markers и progress.

## Допущения

- Русский — основной язык UI; публичные store/product names могут содержать любой пользовательский текст.
- Светлая тема — единственная обязательная тема этого редизайна; системная dark mode не является требованием.
- Media upload выполняется последовательно (`concurrency = 1`) для стабильного порядка, bounded capacity и предсказуемого retry.
- Импорт CSV/XLSX сохраняет текущую бизнес-логику и получает только новый визуальный слой; он не включён в критический путь переработки ручного мастера.
- Root `/` остаётся техническим входом, но больше не должен выглядеть как smoke-test после завершения редизайна.

## Отклонённые решения

- Полностью тёмная тема по умолчанию.
- Декоративные градиенты, неон и glassmorphism.
- Большой desktop-интерфейс в узкой mobile-колонке.
- Stepper как кликабельная замена «Назад/Продолжить».
- Drag-only reorder.
- Автофокус на destructive action.
- Скрытая обложка «первое фото без объяснения».
- Очистка выбранных файлов после частичной ошибки.
- Новый marketplace scope, оплаты или внутренний чат.
